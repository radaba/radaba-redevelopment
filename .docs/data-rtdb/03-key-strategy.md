# Key strategy

- Tower: `tower/{pushKey}`, with `tower_id` as business/display/relationship ID (`tower-repository.ts:4`; `firebase-tower-command-repository.ts:11-17`).
- Assignment: `assignment/{pushKey}`, with `assignment_id` as business ID and `tower_id` as foreign-reference value (`firebase-assignment-command-repository.ts:91-118`).
- Cell: `cell/{pushKey}` with generated `rcell_id = sector_<sector>_<band>_<assignmentId>` (`mobile-assignment-finish-service.mjs:206-212`). Equality-query upsert means duplicate push children can exist.
- Image aggregate: `image/{pushKey}`, selected by child `assignment_id` (`firebase-mobile-image-command-repository.ts:8-10`).
- User/privilege: push-key records; Firebase Auth UID is stored as a child when available and is not the RTDB key (`firebase-admin-data-repository.ts:29-63`).
- Tower audit: Tower push key then audit push key. Administrator audit: global push key.
- Assignment photo ID is generated by the web contract and stored under the Assignment push key. Comment/revisit events use push keys.

No RTDB uniqueness constraint exists. Transactions implement selected application-level uniqueness for Tower IDs and request IDs only.
